# Bickers visual language

The standalone Firebase account page in `firebase/auth-page` uses semantic HTML
for browser password-manager and form accessibility support. Its CSS variables
are generated by `scripts/build-auth-page.mjs` from the actual ThemeProvider
palettes and shared spacing, typography and purpose-based radius tokens. This
is an explicit web adapter; it does not change native primitives or global tokens.

This contract governs every employee and workshop interface. The shared
foundations live in `lib/design`, `providers/ThemeProvider.tsx`,
`components/layout/PageShell.tsx`, and `components/ui/AppPrimitives.js`.
Screens compose those foundations; they do not create competing visual rules.

## Native iOS integration and grouped settings

Timesheets follows Me's text hierarchy: `sectionHeading` is 17/22 bold,
`bodyLargeStrong` is 16/22 bold, and supporting text uses `metadata`.
`SettingsRow` can opt into these via `titleVariant`, `subtitleVariant` and
`titleTone`; existing settings-row defaults remain unchanged.

The approved Apple Settings reference governs settings and preference editors:
use `PageShell appearance="grouped"`, semantic `groupedBackground`, solid
`SettingsGroup` surfaces and `SettingsRow` full-row controls. Grouped surfaces
have no decorative outline or shadow. `settingsRow` uses 17/22 regular text,
`settingsDetail` 15/20 regular, and `settingsSection` 15/20 semibold. Use inset
hairline separators, shared 16pt content insets and purpose-based card corners.
Preserve the brand red as an accent rather than introducing Apple blue.

Existing operational layouts remain on their established components until
explicitly migrated. A settings reference does not authorize restyling dense
editors, charts, documents or all navigation.

Native iOS 26 adapters are centralized in `components/ui/nativeUI.ios.js`:
`NativeActionButton` uses SwiftUI Button, `NativeSettingsSheet` SwiftUI sheet,
and `NativeSegmentedControl` SwiftUI segmented Picker. Native module presence
and OS availability are checked before loading ExpoUI; older binaries and older
iOS use existing shared controls. Reduce Transparency retains native buttons
with bordered styles instead of glass. Android and web never import SwiftUI.
Native actions reuse the existing action lock and disabled/loading contract.
Native secondary actions use the system glass style and capsule material
fallbacks without an added decorative outline. `size="small"` selects native
regular control sizing while preserving the minimum touch target. Pass
`systemImage` for an SF Symbol and `icon` for the existing fallback icon system;
loading replaces the icon with a progress indicator. Existing AppButton
secondary defaults remain unchanged for consumers outside the native adapter.

`NativeTimeSelect` uses the already-linked UIKit compact time picker on iOS,
preserving local HH:mm and the allowed quarter-hour values. Android/web retain
the shared SelectField. `SelectField presentation="settingsRow"` supplies the
solid grouped-row fallback rather than a capsule input; its default is unchanged.

Use genuine native glass for floating/navigation controls and native prominent
actions, not regular content groups or form backgrounds. SwiftUI owns the
native sheet shape and gesture animation; React Native children are hosted via
RNHostView. Busy saves disable gesture dismissal. Native text uses the system's
Dynamic Type defaults; screen-specific fixed fonts must not replace them.
Host measurement, forced themes, enlarged text, VoiceOver and real interactions
require runtime acceptance; web tests do not prove native behaviour.

`EmptyState presentation="grouped"` uses the shared grouped surface and card
radius without changing content spacing. SegmentedControl accepts optional
Feather icons on options; its default appearance and selection contracts remain
unchanged. Schedule uses these shared treatments in both light and dark mode.

`LoadingState presentation="grouped"` uses the same grouped surface and card
radius. PageShell forwards its grouped appearance to the default loading state,
keeping loading and settled surfaces consistent in both themes.

Home uses the same grouped shell and neutral card surfaces in both themes.
`SectionCard tone="grouped"` and `createDashboardCardStyles(colors, "grouped")`
opt into that surface without changing other consumers. Action icons retain
their semantic colours; independent summary cards and lists use the shared card radius.

`Banner presentation="card"` uses the independent card radius while preserving
its semantic status colours. Report an issue uses this variant on its grouped
page shell; form fields and steps retain their existing shared presentation.

`FormStep fullWidth` keeps the numbered marker beside the heading and places
controls beneath it at full content width. Request Holiday opts into this layout;
the default rail layout on other forms is unchanged.

Spec Sheets and Insurance & Compliance share `components/ui/DocumentCard.js`:
grouped surface, shared card corners, red document badge and a View action.
Callers retain their metadata and document-opening logic; long Insurance titles wrap.

The first opt-in pilot is Timesheets > Autofill Settings. Broader migration is
gated on its device acceptance. See `docs/IOS26_NATIVE_UI_AUDIT.md` for version
compatibility, build requirements and the component migration plan.

## Principles

- Light and dark appearance are equally supported.
- Use the native system font on every platform. Do not add a screen-level
  `fontFamily`.
- `#ED1C25` remains the primary brand accent. Use `accentText` for readable
  normal-size accent text and `accentFill` for filled controls with white text.
  These accessible red variants preserve the branding; artwork keeps `accent`.
  Interface code uses semantic theme names instead of literal colours.
- Employee routes use standard density. Workshop routes under `/service/*`
  use compact density.
- Flat sections are the default. Cards represent independent records,
  selectable actions, or self-contained summaries—not ordinary form steps.
- Shared interactive targets are at least 44pt on iOS/web and 48dp on Android.

## Foundations

### Spacing

Use only the shared scale: `0, 2, 4, 8, 12, 16, 20, 24, 32, 40`.
Values above 40 are reserved for structural clearances such as safe areas,
navigation, large media, and scroll endings.

### Density and controls

| Density | Routes | Control height | Card padding | Section gap |
| --- | --- | ---: | ---: | ---: |
| Standard | Employee | 48 | 16 | 16 |
| Compact | Workshop/service | 44 iOS/web, 48 Android | 12 | 12 |

Compact layouts reduce whitespace, never touch-target size. `PageShell`
resolves the workspace default; explicit overrides are temporary migration
exceptions and must be named in the design-system test allowlist.

### Corner radius by purpose

| Purpose | Radius |
| --- | ---: |
| Nested compact control | 8 |
| Button | 12 |
| Single-line text/select/date field | Capsule |
| Multiline field | 18 |
| Independent record/action card | 28 |
| Nested card inside a record or form | 18 |
| Modal or hero surface | 18 |
| Circular icon button | Circle |
| Chip, badge, or bottom navigation | Pill |

Screens must not choose radii decoratively. Use the component for the intended
purpose and let it apply the mapped radius.

For matching rounded rectangles with a uniform inset, use
`getConcentricRadius` from `lib/design/radius.ts`: inner radius is
`max(0, outerRadius - inset)`. Include the outer border in the inset. For
capsules or small bounds, pass `{ width, height }` so the effective outer
radius is clamped before subtraction. For example, a 12pt segmented container
with a 1pt border and 4pt padding has 7pt segments and a 6pt material background
inside each segment's 1pt border. Pill shapes continue to clamp to their actual
dimensions. Asymmetric insets, nonuniform corners, grids, and different shapes
need layout-specific geometry; a fixed `nestedCard` token alone is not proof
of concentricity. Keep existing radius names for compatibility; `lg`/`xl` are
legacy aliases, not an ordered size scale.

### Typography

Use `AppText` variants. `tone` and `align` are the only appearance choices.
`layoutStyle` may control layout and truncation, but must not redefine colour,
font size, line height, letter spacing, weight, or family.

| Variant | Size / line | Weight | Use |
| --- | --- | --- | --- |
| `micro` | 9 / 11 | 700 | Dense auxiliary labels |
| `caption` | 11 / 14 | 600 | Supporting copy |
| `metadata` | 12 / 16 | 600 | Dates, counts, identifiers |
| `formLabel` | 13 / 18 | 600 | Persistent field labels |
| `body`, `bodyStrong` | 14 / 20 | 400 / 600 | Default content |
| `bodyLarge` | 16 / 22 | 400 | Emphasised body content |
| `sectionTitle` | 17 / 22 | 600 | Section headings |
| `titleSmall` | 20 / 26 | 600 | Compact page titles |
| `pageTitle` | 24 / 30 | 700 | Hero page titles |
| `display` | 30 / 36 | 700 | Rare dashboard emphasis |
| `button` | 14 / 20 | 600 | All labelled buttons |

Headings use size-specific negative tracking (−0.2 to −0.6pt). Body copy
keeps natural spacing. Weight expresses hierarchy without a heavy black face.

## Component contracts

### Pages and surfaces

- Use `PageShell` for safe areas, responsive gutters, width constraints,
  scrolling, keyboard avoidance, refresh, and asynchronous page states.
- Use `PageSection` for continuous content. It may use a heading and divider,
  but has no surrounding card surface.
- Use `FormStep` for numbered workflows. Its rail connects related fields
  without wrapping each step in a card.
- Use `SectionCard` only for an independent record, selectable action, or
  self-contained summary. Default cards are flat, bordered, and shadow-free.
- Use `ListRow` for record-shaped list content. It owns selected, disabled,
  divider, status, metadata, trailing content, chevron, and full-row action
  behaviour; screens only arrange rows.
- On compact viewports or enlarged text, list statuses sit beneath the copy.
  Status labels wrap within the available width; they must not displace the
  record title. Shared checkbox labels, form help, modal headings and action
  buttons also wrap instead of overflowing their containers.
- Shadows are reserved for modals, floating navigation, and transient overlays.

### Buttons

Use `AppButton` or `IconButton`; do not rebuild button visuals in a screen.

`AppButton` defaults to the shared capsule shape in both themes and on every
platform. Use `pill={false}` only for an intentional control-shaped exception;
explicit radius overrides remain supported. Colours, density, disabled/loading
states and action behaviour continue to come from the shared component.

- `primary`: accent fill with inverse text.
- `secondary`: alternate surface, standard border, primary text.
- `ghost`: transparent surface and border with accent text.
- `danger`: danger fill with inverse text.
- `glassPrimary`: brand-tinted native Liquid Glass with inverse text for a
  prominent action on a material surface. Older iOS uses tinted native blur;
  Reduce Transparency and Android use the opaque brand fallback. This is an
  explicit variant; ordinary primary buttons retain their existing appearance.
- Standard buttons are 48pt; compact and icon buttons are 44pt on iOS/web and
  48dp on Android. Shared spacing and typography remain the same.
- Icon buttons are circular; screens must not stretch or reshape them.
- Loading, disabled, pressed, focus, icon sizing, and action locking belong to
  the shared component.
- Both button types await asynchronous actions and reject duplicate taps.
  Handle rejected actions through `onError(error)`; do not recreate pending
  state solely to lock a shared button.

### Forms

- Use `FormField`, `TextArea`, `SelectField`, `DateField`, and
  `SegmentedControl`.
- Every field has a persistent label; placeholder text never replaces a label.
- Fields use a 1pt semantic border, capsule shape (18pt for multiline), density-based height, and a 2pt
  focus ring. Errors use `danger`; disabled fields retain readable contrast.
- `SelectField` owns its selector when given controlled `value`, `onChange`, and
  `{ label, value, description?, disabled?, keywords? }[]` options. Search,
  loading, empty, long-list, and disabled-option states stay inside the field.
- `SelectField material` opts a tappable selector into the shared native glass
  surface, with the existing platform and reduced-transparency fallbacks.
  Use it for material settings controls, not editable text-entry backgrounds.
- `DateField` owns its calendar and exchanges local dates only as canonical
  `YYYY-MM-DD` strings. Minimum, maximum, disabled, and clearable states belong
  to the field; screens must not apply timezone conversion.
- Screen styles may position fields but must not restyle their typography,
  colours, radius, border, or height.
- Use `AppCalendar` for calendar grids and `ToggleRow` for labelled boolean
  settings. Calendar theme objects and local switch colours are not screen APIs.

### Media and identity

- Use `Avatar`, `IconBadge`, and `MediaThumbnail` for identity, icon, and media
  presentation. Screens may own media dimensions and aspect ratio through
  `layoutStyle`; borders, overlays, fallbacks, and badges belong to the shared
  primitive.
- Fixed brand artwork belongs in `components/renderers`. A renderer may contain
  the exact colours required by an artwork, chart, or document canvas, but it
  must not export a general-purpose palette to application code.

### Feedback, status, and modals

- Use `Banner` for semantic information, success, warning, and danger feedback.
  Its text, surface and border use the same contrast-checked palette as status chips.
  Actions and dismissal use its shared affordances.
- Use `StatusChip` and the central status palette for workflow state. Never
  infer status colours in a screen.
- Use `StateView` or `PageShell.state` for loading, empty, error, success, and
  retry UI.
- During an explicit refresh, scrollable native `PageShell` pages use the
  system pull-to-refresh indicator alone. Inline “Updating…” feedback remains
  for background resource updates, static pages and web. Refresh errors retain
  their message and Retry action in every mode.
- Use `AppModal` and `ConfirmDialog` for editor, picker, detail, and
  confirmation overlays. Use `MediaViewerModal` for full-screen receipt and
  inspection media; media must not be forced into a dialog-shaped surface.
- Modals use the elevated surface, 18pt radius, semantic overlay, shared
  header, scrollable body, and ordered actions. Presentation is a bottom sheet
  on phones and a centred dialog on tablet/web. Busy confirmations cannot
  dismiss or submit twice. Sheets observe the device’s reduced-motion setting,
  including changes while the app is open; reduced motion removes the slide.

### Interaction states

- Visual state resolves in one order: `error → focused → selected → default`.
- Disabled and loading states block input, expose the matching accessibility
  state, and apply the shared inactive opacity.
- Screens may provide business validation and action callbacks; they must not
  reproduce shared pressed, focused, disabled, loading, or error visuals.

### Navigation

- Employee and service workspaces use Expo Router Native Tabs on iOS. Apple owns the glass material, selection animation, sizing and accessibility behaviour. Other platforms retain the shared custom bottom bar.
- Both workspaces have at most five tabs. The custom fallback is 68pt high and no wider than 520pt.
- Icons, labels, badges, selected state, focus, and haptics belong to
  `BottomNavigationBar`.
- Navigation always uses semantic theme surfaces in both appearances.

### Platform materials and feedback

- iOS controls use native `expo-glass-effect` only when both Liquid Glass and
  effect API availability checks succeed. Native effects receive their own
  corner shape; clipping a wrapper does not configure UIKit refraction.
- Earlier iOS uses native chrome blur when transparency is allowed. Reduce
  Transparency uses an opaque elevated surface. Android uses opaque tonal
  surfaces, native ripple feedback, and existing Android elevation tokens.
  Web retains its existing fallback presentation.
- Use glass selectively for navigation and interactive controls, not content
  cards or nested glass layers. Do not add blur to Android to mimic iOS.
- ThemeProvider owns reduced transparency; `useReducedMotion` owns the motion
  preference. Navigation stacks and adaptive sheets honour reduced motion.
  Native Android stack transitions use the platform default.
- Platform metrics live in `lib/design/platform.ts` and flow through shared
  tokens. Colours, spacing, typography and radius geometry are shared.
  Platform component files are warranted for different native APIs; simple
  styling policies do not require duplicate components or screens.
- `t.motion`, `t.opacity`, and `t.materials` own shared durations, interaction
  opacity and blur intensity. Android keyboard resizing is explicit in
  app.json; PageShell owns keyboard and safe-area clearances.

## Prohibited patterns

- Local `COLORS` or general-purpose palettes.
- `staticColors` for ordinary interface styling.
- Raw or screen-selected colours, font metrics, radii, control heights, or
  standard spacing.
- Directly styled generic buttons, inputs, cards, status pills, or modals.
- React Native `TextInput` or `Modal` imports in screens; shared controls own
  field states, async locking, focus, errors, and adaptive overlays.
- Cards used only to separate consecutive fields or text sections.
- Platform-specific visual variants that weaken light/dark parity.
- Passing arbitrary visual `style` overrides into shared primitives. Use
  explicit semantic props plus `layoutStyle`.

## Screen styling boundary

Screen-owned styles are layout only. Approved properties cover flex/grid
arrangement, alignment, positioning, token-based spacing, responsive
dimensions, aspect ratio, overflow, and transforms. Colours, borders, shadows,
opacity, radii, font metrics, and component chrome belong to the semantic theme
or a shared primitive.

The local ESLint design-system rules apply immediately to new routes and every
route marked complete in `tests/designSystemMigrationManifest.js`. Pending
routes may retain only the exact exceptions already named in
`tests/designSystemLegacyBaseline.js`; those sets can shrink but cannot grow. A
route cannot be marked complete until all of its exception categories are gone.

Existing legacy exceptions are recorded by exact file path in the automated
design-system baseline. The baseline may shrink during migration and must never
grow without an explicit contract change.

## Automated enforcement

- Every UI-bearing route must import and render `PageShell`. Structural routes
  such as layouts, redirects, aliases, and full-screen media viewers must be
  listed with a reason in `scripts/design-system/enforcement-config.cjs`.
- Routes never pass a `density` prop. `resolvePageDensity` selects standard for
  employee routes and compact for `/service/*` routes, and repository tests
  verify every registered route.
- React Native `TextInput` is owned only by the exact shared implementation
  paths in the enforcement registry. Direct, aliased, namespace, and JSX access
  elsewhere fails lint.
- Screens may use only semantic `colors.<name>` members and literal approved
  `AppText` variants. Computed colour access, unknown semantic names, dynamic
  screen variants, fixed interface colours, and local generic control chrome
  fail lint.
- Permanent fixed-colour renderers require an exact path, one of the approved
  `chart`, `document`, or `brandArtwork` categories, and a justification. An
  application screen can never be a permanent renderer exception.

## Visual regression checks

`npm run test:visual` builds the deterministic visual export and compares the
five fixture scenarios in light and dark at 390×844 and 820×1180. Chromium uses
device scale factor 1, disables animations, hides carets, and waits for fonts.
The resulting 20 committed baselines fail when more than 0.5% of pixels differ.

Baselines never update during normal tests. Use
`npm run test:visual:update` deliberately, then review every changed image and
diff artifact before committing. Visual-test authentication bypass is limited
to the two exact showcase routes and is enabled only when
`EXPO_PUBLIC_VISUAL_TEST_MODE=1`; ordinary and production exports fail closed.

The additional `responsive-controls.spec.js` checks long content at 320, 390,
and 820px in both themes and workspace densities. It measures rendered
containment, exercises checkbox state and text entry, and opens/closes an
adaptive modal with long headings and actions. These fixtures validate shared
controls; authenticated route workflows still need their own coverage.

### Native switches and live text scaling

`ToggleRow` uses the native React Native `Switch` on iOS and Android, with one
labelled switch and platform minimum touch targets. Use `leadingIcon` when
composing an icon-led settings list so text columns remain aligned. Web keeps
the accessible custom switch.

Shared `AppText` and button labels refresh their native iOS text view when the
system font scale changes, allowing live Dynamic Type remeasurement without
remounting the screen or resetting form state. List row copy can wrap beyond
two lines at accessibility sizes. Form input values are not remounted.

### Verified semantic migration contracts (13 October 2026, round 2)

An explicitly supplied `AppText tone` takes precedence over legacy style colour.
Omitting `tone` retains compatibility with legacy style precedence. Keep typography
in established variants; do not use this contract to introduce new screen metrics.
`SectionCard tone="subtle"` uses the existing `surfaceAlt` semantic surface with
unchanged border and corner geometry. Its default tone continues to use `surface`.
Use `RecordDetailRow` for the identical compact read-only label/value pattern in
workshop records; value formatting stays with the caller. It does not replace
editable fields or differently grouped accessible rows.

Current migration evidence and remaining limitations are recorded in
[the second-round report](docs/DESIGN_SYSTEM_COMPLIANCE_ROUND2.md).

### Document frames and record separators (Round 3)

Use `DocumentSurface` for document-viewer content and loading/error frames.
Its default `page` variant uses the page background; `embedded` uses the alternate
surface and a top hairline border. Caller-owned layout does not redefine chrome.
Keep document rendering, URL handling and loading/error behaviour with the caller.
Use `Divider variant="record"` between read-only record sections: it retains the
existing full-point, subdued border-colour rule. Ordinary dividers keep their
hairline contract. Insets remain token-based layout. See
[Round 3 evidence and limitations](docs/DESIGN_SYSTEM_COMPLIANCE_ROUND3.md).


### Chronological time options (Round 4)

`TimeChoiceRow({ label, selected = false, disabled = false, onPress })` owns the
centred time-option presentation shared by Week Editor's time and pre-call
pickers. Callers own label formatting, next-day offsets, option ordering,
scrolling, selected value, selection updates and modal dismissal. The component
retains the existing selected accentSoft surface/accent separator/check, normal
border separator, 400/800 text emphasis and 15pt check. Horizontal inset and
check offset use existing spacing tokens. It adds no accessibility grouping,
role, rounding, clipping or state storage. `AppPressable` supplies the existing
platform target minimum, disabled treatment, focus and Android ripple.

This contract is deliberately narrower than a record ListRow or general
SelectField; those have different layout and selection semantics. Do not replace
different chronological controls solely because they display times. The legacy
42pt nominal list measurement is preserved; native FlatList scrolling at the
shared 44pt/48dp target minimum still needs manual acceptance before changing its
measurement. See [Round 4 evidence and blockers](docs/DESIGN_SYSTEM_COMPLIANCE_ROUND4.md).


Single-line `FormField` text is vertically centred. iOS retains native font
metrics without an imposed paragraph line height; Android uses centre alignment
without extra font padding. Multiline notes remain top aligned. Password values,
visibility actions and input callbacks retain the existing shared APIs.


### Shared card surfaces

`lib/design/cardSurface.js` owns the ordinary card surface, semantic border colour,
1 pt border and independent card radius. `SectionCard` and `DocumentCard` consume
this rule. `getCardSurfaceStyle(colors)` is the supported visual-only adapter for
existing bespoke wrappers: keep their padding, sizes, flex layout, accessibility
and event handlers intact. Screen styles must not duplicate those four surface
properties for ordinary cards. Status-coloured board events, calendar marks,
fields, modal shells, transparent sections and nested controls remain distinct.
Use `borderTone` for semantic warning/error borders, `borderAccent` to retain a
product status colour, and `inset` for concentric
nested geometry when applicable. Neither option changes content or behaviour.

`SettingsGroup outlined` adopts the same independent card border. Work-side
record groups opt in; the default borderless inset-list contract is preserved
for existing consumers, including Service-side screens.
